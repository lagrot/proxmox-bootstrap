HOMELAB UPDATE QUICK GUIDE
==========================

CONTAINER TARGETS
-----------------
  ct200 = Debian Security packages in the Docker/Frigate LXC
  ct210 = Debian Security packages in the MQTT LXC
  ct220 = Debian Security packages in the Hermes LXC
  ct230 = Debian Security packages in the Cloudflare gateway LXC
  ct240 = Debian Security packages in the Landet viewer LXC

The target selects the LXC and its validation tests. It is not an application
upgrade command.

PACKAGE SCOPE
-------------
Only installed packages offered by Debian Security are updated.

  ct200 excludes Docker Engine/Compose from download.docker.com and the
        pinned Frigate image.
  ct210 may include Mosquitto when Debian Security publishes a fix because
        Mosquitto is installed as a native Debian package.
  ct220 excludes the Hermes application, which is not a Debian package.
  ct230 excludes cloudflared from the third-party Cloudflare repository.
  ct240 updates eligible Debian dependencies, not the viewer release or go2rtc.

ROLLBACK PROTECTION
-------------------
CT 200 cannot use an LXC snapshot because of its /mnt/frigate bind mount.
The updater therefore creates a stopped full-rootfs backup before patching.
Camera media is not copied or changed.

CT 210, CT 220, CT 230 and CT 240 use temporary Proxmox LXC snapshots.
A patch with pending updates stops/restarts the selected snapshot-protected CT.
For CT230 this briefly interrupts BOTH public Cloudflare routes.
SSH/Tailscale to the host remains the maintenance access path.

BACKUPS
-------
Weekly recovery backups are a separate Step 12 operation. They retain eight
validated sets. CT 200 security updates additionally keep one temporary
full-rootfs rollback backup until cleanup.

Check backup and update status:
  bash scripts/step20-status.sh

SECURITY UPDATE
---------------
Update one container at a time.

Optional. Refresh package metadata and preview without installing anything:
  bash scripts/step20-update-ct.sh ct210 --dry-run

Patch. This repeats discovery, creates rollback protection, installs Debian
Security updates and verifies the selected service:
  bash scripts/step20-update-ct.sh ct210 --confirm

After at least 24 hours, verify the service again and delete rollback protection:
  bash scripts/step20-update-ct.sh ct210 --cleanup

For other targets, replace ct210 with ct200, ct220, ct230, or ct240. The script chooses
the correct rollback type automatically.

The script remembers the exact snapshot or backup path.

If an update or validation fails, the script stops and keeps rollback
protection. It never rolls back automatically.

CHECK SNAPSHOTS
---------------
CT 210, CT 220, CT 230 and CT 240 use snapshots:
  pct listsnapshot 210

ROLL BACK A FAILED CT210 UPDATE
--------------------------------
Only do this when the update failed and the retained snapshot was inspected.
EXACT_SNAPSHOT_NAME is the name beginning with pbsec- shown above.

  pct stop 210
  pct rollback 210 EXACT_SNAPSHOT_NAME
  pct start 210
  bash scripts/step20c-post-update-validation.sh ct210

Rollback was tested successfully on CT 210. It restores the pre-update
packages and configuration. It does not automatically retry the update.

ROLL BACK A FAILED CT200 UPDATE
-------------------------------
The failed command prints the exact backup archive path. It is also the
backup_archive= value in:
  cat /var/lib/proxmox-bootstrap/security-updates/ct200.state

Use that exact path as CT200_BACKUP below:
  pct stop 200
  pct restore 200 CT200_BACKUP --force 1 --storage local-lvm
  pct start 200
  bash scripts/step20c-post-update-validation.sh ct200

This restores CT 200's root filesystem and configuration. It does not restore,
delete, or change camera media under /mnt/frigate.

TROUBLESHOOTING
---------------
Validate the controlled Debian Security policy:
  bash scripts/step20g-unattended-upgrades-validation.sh ct210

Check MQTT:
  bash scripts/step20c-post-update-validation.sh ct210

Inspect package health without repairing anything:
  pct exec 210 -- dpkg --audit
  pct exec 210 -- apt-get check

If validation or package health fails, stop and inspect the error. Do not
delete the rollback snapshot/backup or run package repair commands blindly.

NOT INCLUDED
------------
This workflow does not update Proxmox, Home Assistant, Docker Engine/Compose
packages from download.docker.com, Frigate images, Hermes application
releases, or Zigbee firmware.

CT230 / CT240 INITIAL POLICY SETUP
--------------------------------
Run once per guest, one at a time. This installs unattended-upgrades tooling
and dependencies, but disables automatic installation/reboots. It is NOT a
security patch command. A running-guest snapshot protects setup, and service
validation runs before and after it. Reapply is a no-op when policy is valid.

  bash scripts/step20f-unattended-upgrades.sh --dry-run --target ct240
  bash scripts/step20f-unattended-upgrades.sh --confirm-install --target ct240

Replace ct240 with ct230 for the gateway. Default setup without --target still
selects only the original CT200/210/220 group. Policy validation 'all' includes
all five guests.

The shared maintenance/backup locks and target-specific Cloudflare/Landet locks
prevent overlapping patching, backups, application deployment and publication.
Existing CT230/CT240 application/baseline/policy snapshots are preserved. An
orphaned pbsec- snapshot blocks patching until inspected. Policy-setup snapshots
(pbpolicy-) remain separate from updater-managed snapshots; inspect and remove
only the exact setup snapshot after at least 24 hours and successful validation.

Real target routing, policy setup, repeat-apply, and patch preview are verified.
CT230 production security patching and post-update route/service validation
have passed after a guarded pre-install readiness retry. CT240 remains current
with no pending security packages. Install/post-validation failure and cleanup
paths are tested in isolation; no production security-patch rollback drill is
claimed for CT230/CT240.

STARTUP READINESS AND PRE-INSTALL RETRY
--------------------------------------
CT230/CT240 wait up to 120 seconds for their own services before full validation.
Full route/source validation has up to three attempts to allow reconnects. A
persistent failure still stops the updater and retains rollback protection.

If these targets failed specifically at post-protection-baseline (before any
package installation), repeat --dry-run or --confirm. The updater verifies the
exact retained snapshot/state and reuses it without another shutdown. Failed
installation or final validation is never resumed automatically; inspect first.
